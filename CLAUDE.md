# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

An Obsidian vault used to build and study a Q&A bank for a Claude Code / Claude API certification exam. The content itself has no build system, linter, or test suite — it's a vault of Markdown notes. A small uv-managed Python package, `src/claude_exam`, backs the vault-lookup tooling (card search/parsing, an MCP server) that the `.claude/skills/` skills use to serve the notes.

## Structure

- `Questions/<Topic>/<Question Title>.md` — the Q&A bank. Topics currently: Agents and Workflows, Applications & Integration & Orchestration, Claude, Context Management & Reliability, Eval Testing Debug, Model selection and Optimization, Prompt and Context Engineering, Security and Safety, Tools and MCPs. No question files sit directly under `Questions/` uncategorized anymore — every card lives in a topic folder.
- `Templates/Question_Template.md` — the Obsidian template for new question cards (configured as the templates folder in `.obsidian/templates.json`). It only contains the section skeleton (`### Question` / `### Answer` / `##### Explanation` / `##### References`) — the YAML tags frontmatter and `# <Title>` heading are added by hand per file, not by the template.
- `Docs/` — free-standing Anthropic SDK reference notes. `Docs/ICA/` holds the IBM Consulting Advantage API reference (`README.md` summary plus the full `openapi.yaml`) used by the `/ica` routes in `src/claude_exam/api/`.
- `.obsidian/` — Obsidian app config; not relevant to editing content.

## Question card format

Every file in `Questions/` follows this exact fixed structure — preserve it when adding or editing cards:

```
---
tags:
  - topic-slug
  - keyword-slug
  - ...
---

# <Title matching the filename>

### Question
<scenario/question text, may include a code block>
### Answer
<the correct answer, stated as a decision plus its direct justification>
##### Explanation
<2-3 short paragraphs justifying the answer>
##### References
<one or more docs links, one per line with a trailing double-space/line-break>
```

Tags are topic/keyword slugs (kebab-case) used for Obsidian's tag pane/search, not a controlled vocabulary — reuse existing tags across files where the topic overlaps rather than inventing near-duplicates.

A card's `##### References` section ends with an extra `Roadmap: [[Step Title]]` line, wikilinking the matching note under `roadmap/` (see below) — this gives study context for where the question's problem sits on the certification learning path. A card may also carry a roadmap-leaf-derived tag (kebab-case slug of that same `Step Title`) alongside its topic/keyword tags, added only when no existing tag already covers the same concept. The `.claude/skills/roadmap-linker/` skill applies both additions to new or edited cards.

A card may optionally also carry a `rating` frontmatter property (integer 0-100, a self-assessed "how well do I understand this" score, overwritten on each save) and a trailing `##### Notes` section (a dated bullet log, e.g. `- **2026-08-29**: kept mixing up X and Y`, appended to — never overwritten — on each save). Both are absent on most cards; they're written by the `.claude/skills/rate-card/` skill via the MCP server's `update_card` tool, never added by hand.

Within Question/Answer/Explanation prose, `==highlight==` marks the phrase(s) that correlate a Question's decisive fact to the phrase in the Answer/Explanation that resolves it (sparingly — often just one span per section); `**bold**` is a separate, older convention that bolds the single Explanation sentence restating the answer. The two never overlap. The `.claude/skills/keyword-highlighter/` skill applies the former to new or edited cards.

## `roadmap/` and `public/roadmap.yaml`

`public/roadmap.yaml` is the certification study roadmap: a nested list of `title` (+ optional `children`) nodes, in learning-path order. `src/claude_exam/roadmap_gen.py` (re)generates the `roadmap/` folder from it — one folder + index/MOC note (`## Steps` linking to its children) per branch, one plain note (`Part of: [[Parent]]`) per leaf. Regenerate after editing the YAML with:

```
uv run python -m claude_exam.roadmap_gen
```

This wipes and rewrites `roadmap/` from scratch, so make structural edits in `roadmap.yaml`, not directly in the generated notes.

## `src/claude_exam` and the `claude-exam-vault` MCP server

`src/claude_exam/vault_scan.py` parses every `Questions/**/*.md` file into a `Card` (title, tags, question, answer, explanation, references, rating, notes) and scores cards against a query by title/tag/question overlap (`search_cards()`). It also holds the vault's only write helpers, `set_card_rating()` and `append_card_note()`, which do targeted in-place edits (never a full frontmatter/body re-serialization) so untouched lines stay byte-identical. Two things sit on top of it:

- `src/claude_exam/search_cards.py` — a CLI (`uv run python -m claude_exam.search_cards "<query>"`) used by the `short-question-answer` skill via Bash.
- `src/claude_exam/mcp_server.py` — the MCP server (registered in `.mcp.json` as `claude-exam-vault`), mostly a thin retrieval layer exposing `search_vault`, `get_card`, and `list_topics`, plus one narrow write tool, `update_card(relpath, rating=None, notes=None)`, used by the `rate-card` skill. No LLM calls happen inside the server; any rephrasing/explaining/reasoning about what to write is done by the calling skill itself.

`extract.py`, `section_map.py`, `explanation_parse.py`, and `html_clean.py` are a separate, one-off pipeline that converts raw practice-exam JSON (`public/*.json`) into staged candidate cards (`.staging/*.pending.json`) — unrelated to the lookup tooling above. Turning a staged record into an actual `Questions/**/*.md` file is a manual/agent-driven step, not a script — see the `promote-staged-cards` skill below.

## Game API (`/v1/game`) for the Unity client

Layers: `routers/game.py` (thin HTTP handlers) → `api/game/service.py` (`GameService`, the round rules; raises the `ApiError`s in `api/game/errors.py`) → `api/game/repository.py` (`QuestionRepository`, `RoundRepository`: the only MongoDB access, each write one conditional update) and `api/game/domain.py` (pure rules: `is_playable`, `correct_indices`, `round_entry`, `PLAYABLE_QUERY`, constants). `get_game_service` in `dependencies.py` builds the service from the collection dependencies, so tests still override the collections. `api/search.py` imports the rules from `game/domain.py`, never from a router.

The game and search routes exist only under `/v1` (`main.py`); there are no unversioned `/game` or `/search` paths. A breaking change to the game contract goes to a new prefix. No auth (the game routes must stay open), no CORS (native builds don't need it; WebGL would). Responses are flat, null-free objects with lists wrapped in `items`, because `JsonUtility` can't parse a top-level array or null.

**Errors** from every route are `{"detail": "<string>", "code": "<code>"}` (`api/errors.py`); validation errors also carry FastAPI's list in `errors`. Game codes: `round_not_found`, `question_not_found`, `simplified_not_found`, `question_not_in_round`, `question_not_answered`, `no_questions` (404); `already_answered`, `no_fifty_fifty_charges`, `too_few_answers`, `round_full`, `batch_out_of_order`, `round_changed` (409; `round_changed` means "retry"); `answer_out_of_range`, `answer_eliminated`, `question_not_playable`, `validation_error` (422); `rate_limited` (429). Other `HTTPException`s get `http_<status>`.

**No `/game` response reveals the answer key before the question is answered.** The game plays rounds; the round document in `game_rounds` (layout documented in `game/repository.py`) keeps the correct index, answer count, review and whether its rephrase was offered per question, every question id in `question_ids`, the batches handed out, the filters, and what has been answered and eliminated (TTL index on `created_at`: rounds expire after `ROUND_TTL_SECONDS`, a day). A round holds at most `MAX_ROUND_QUESTIONS` (500).

- `POST /v1/game/rounds {count=10, section="", assessment_type=""}` → 201 `{round_id, items: GameQuestion[], simplified: GameQuestion[], total, fifty_fifty_charges}`. Samples `count * OVERSAMPLE_FACTOR` and keeps the first `count` playable questions (`is_playable`: 2..4 answers, exactly one valid correct letter); offers a question's rephrase (`simplified`, see "The rephrase") only if it keeps the answer count and the correct answer and its check did not find it `changed` (`simplified_matches`). `total` counts the pre-filter matches, so `total > len(items)` means batches can follow. 404 `no_questions` (and nothing stored) when none match. Empty strings mean "any". Rate limited (30/min per client, in process memory).
- `POST /v1/game/rounds/{round_id}/batches {batch_index, count=10}` → `{batch_index, items, simplified, remaining}`: the round's next questions, none already in it (started, searched or earlier batches), with the round's filters; empty `items` once the pool is used up (not stored). Batch 0 is the start, so the first call sends 1; asking for an existing batch returns it again (a retry), a later one is 409 `batch_out_of_order`; a concurrent add makes the write miss (409 `round_changed`).
- `POST /v1/game/rounds/{round_id}/answers {question_id, answer_index}` → `{question_id, answer_index, is_correct, correct_index, original: {explanation, feedbacks[]}, misconception, outcome, resolution}` (a rephrase has no review of its own). One atomic `find_one_and_update`, so a question counts once. The same answer again repeats the result; another answer is 409 `already_answered`, and the client then reads the recorded one with:
- `GET /v1/game/rounds/{round_id}/answers/{question_id}` → the same `GameAnswerResult` for the answer the round recorded (404 `question_not_answered` if none). This is how a lost answer response is recovered.
- `POST /v1/game/rounds/{round_id}/fifty-fifty {question_id}` → `{question_id, eliminated_indices, fifty_fifty_remaining}`: two random wrong answers, once per unanswered question (asking again repeats the result), at most `FIFTY_FIFTY_CHARGES` (2) per round. The game takes `fifty_fifty_remaining` as the count.
- `POST /v1/game/rounds/{round_id}/questions {question_id}` → `{item: GameQuestion, simplified: GameQuestion[]}` (0 or 1 simplified): adds a question (the game's search result) to the round, conditionally, so adding one it already has changes nothing and returns it again (offering the rephrase only if the round offered it when the question was added). 409 `round_full`, 422 `question_not_playable`.
- `question_id` in request bodies and paths must be a 24-char ObjectId hex string (`OBJECT_ID_PATTERN` / `GameQuestionId`), which also keeps it safe as a key in the round document's field paths.
- Browsing, without answer keys, playable questions only: `GET /v1/game/questions?count=10&section=&assessment_type=&shuffle=true` → `{items: GameQuestion[], total}` (`count` 1–50), `GET /v1/game/questions/{id}`, `GET /v1/game/simplified-questions?…`, `GET /v1/game/simplified-questions/{question_id}` (404 `simplified_not_found`), `GET /v1/game/sections?simplified=false` → `{items: string[]}`.

`GameQuestion` = `id, simplified, section, assessment_type, question, answers[{index,text}]` plus entities, parts, flow and story fields. A rephrase keeps the examination `id` and sets `simplified: true`. The stored `correct_response` letters (`"a"`, `"b"`…) are converted to indices on the server only. `examination_simplified.question_id` is the examination `_id` as a *string* (not an ObjectId); the code always joins through `str(_id)`.

The answer key is otherwise served by the study routes (`/questions`, `/examination`, `/ica`, `/v1/search/questions`). Setting `API_KEY` makes them require an `X-API-Key` header (`security.require_api_key`, applied at router level; the key is read into `app.state.api_key` at startup). Lives and score live in the client, so a determined player can still learn an answer by answering it in a throwaway round; move them into the round document if a leaderboard ever depends on them.

Indexes are created at startup by `api/indexes.py` (`ensure_indexes`); one whose options changed (e.g. new text weights) is logged, not fatal, and has to be dropped by hand to apply. The app uses a single `AsyncMongoClient`.

Tests (`uv run --with pytest pytest`): `tests/test_game.py` (routes over `tests/fakes.py`, in-memory collections implementing the operators the repository sends, with MongoDB's array semantics), `tests/test_game_mongo.py` (the service and repository against a real MongoDB in a throwaway database; opt-in with `TEST_MONGO_URL=mongodb://127.0.0.1:27017`), and `tests/test_contract.py`: real responses pinned in `tests/contract/*.json` plus the game's OpenAPI schema (`openapi_game.json`), and the same JSON written to `../exam-cards-game/Assets/Tests/EditMode/Contract/` for the Unity contract tests. After an intended contract change run `UPDATE_CONTRACT=1 uv run --with pytest pytest tests/test_contract.py` and commit both repos. `tests/conftest.py` resets rate limits, the API key and dependency overrides per test.

## Ingest: from an uploaded file to a playable question

One upload does everything for a new question, with no hand work. The runbook is the `ingest-exam` skill (`.claude/skills/ingest-exam/SKILL.md`); the sections below describe each step.

- **Import** (`POST /examination/import`, `routers/examination.py`): `normalization.normalize_result` strips HTML and stores `text_hash` (`scenario_catalog.text_hash` of the question and its answers; unique sparse index, filled in for older questions at startup by `indexes.ensure_text_hashes`). A question whose hash the bank holds, or that occurs earlier in the file, is left out, so a file can be uploaded again. `ingest.plan_import` builds the report in `ImportResult`: `new`, `duplicates`, `unplayable`, `chapters`, `without_scenario`, `unknown_scenarios` (paragraphs no chapter claims) and `unknown_sections` (no objectives in the catalog). `?dry_run=true` returns the report and stores nothing; `?simplify=false` stores the questions without starting the job.
- **The job** (`batch.py`): the import starts job mode `full`, whose steps are `objectives → story → decompose → beat → icons → flow → resolve → rephrase → check` (`batch.STAGES`; objectives first because the story step orders a question by its difficulty; the decomposition, which also builds the question's semantic parts and visual entities in code, before what is built on it: the icons of its entities, the pre-answer flow and the resolution that continues it; the beat after the story, whose stage it reads, and the decomposition, whose answer-only entities its leak check uses; the rephrase is optional, last, set after the beat, and checked). A failed step is recorded (`errors`, `stages_failed`) and the question goes on with the steps that do not need it (`batch._NEEDS`: the beat needs the story, icons and flow the decomposition, resolve the flow, check the rephrase). `PIPELINE_CONCURRENCY` (default 3) questions run at the same time; the steps of one question stay in order. Every step asks the model through `ica_json.ask_json`, which requests a JSON object (`response_format`) and rejects an unfinished reply; the decomposition, beat, flow, resolution and rephrase go through `ica_json.ask_validated` (the reply, its gate, and up to 3 replies with `repair_note`); the first three also send a strict `json_schema` (best effort on ICA, so their prompts carry `schema_skeleton` too). Job modes for backfills: `decompose` (`decompose, icons, flow, resolve`), `icons`, `flow`, `resolve`, `rephrase` (`rephrase, check`), `check`, `objectives`, `story` (`story, beat`), `beat`; `run_simplification_job(stages=...)` runs any steps in any order. Stored jobs of removed modes (`simplify`, `entities`) still read.
- **No answer key in pre-answer content** (`api/question_view.py`): every step whose output a player sees before answering (decompose with its parts and entities, icons, flow, beat, rephrase) and the check that answers without the key build their messages from `KeyFreeQuestion` (`key_free(doc)`: section, scenario paragraph, stem, whole question, answers): it has no field for the correct answer, the feedback or the explanation, so their prompt builders cannot leak them. The key is not secret (the study routes serve it); the point is that content shown before answering must not be written with it in view. Only objectives, the story (stage and the lines after the answer) and the resolution read the examination record itself. `tests/test_key_free.py` puts sentinel strings in the key, feedback and explanation and checks no pre-answer prompt carries them.
- **No answer given away in pre-answer text** (`api/leaks.py`, the one definition): a text shown before answering leaks when it names an entity only an answer option names (`answer_only_entities`: the decomposition entities the scenario paragraph and stem do not name) or contains an answer's text (at least `MIN_ANSWER_CHARS`, 20, and not already in the scenario or stem). `answer_only(question, decomposition=None)` computes the terms once (`AnswerOnly`: `entities`, `answers`, and `proposed`, the entities an answer actually names); `leak(text, terms)` tests one text; `leak_errors` makes gate messages. Texts written from the raw question test against `AnswerOnly.narrow()` (only `proposed`: an entity no text names is the model's own word, which such a text may reuse): the decomposition gate (scenario facts), `decompose.parts_from` (a leaking part is dropped), the beat gate and the rephrase gate (`rephrase.leak_errors`: the rephrased question; with the job's decomposition when there is one). The flow gate (labels) and `flow.flow_from` keep the wide set: the flow is drawn from `scenario_view`, where those entities are gone. The decomposition gate now also refuses a scenario fact that repeats an answer's text, a rule it did not have before. `points_at_correct` is the soft check behind `flow.leak_warning`; the caller passes the correct index, so the module never reads the key. Tests: `tests/test_leaks.py`.
- **Input keys** (what decides whether a step is done): every step stores an input key (`api/step_key.py`): a hash of the exact system and user messages it sent (the first attempt's; repair notes and the reply format are not in it) plus the module's `CODE_VERSION`. The fields are `input_key` on each record (objectives, story, decomposition, rephrase), `icons_input_key` / `flow_input_key` / `resolution_input_key` on the decomposition record and `check.input_key`. `pipeline_keys.is_current` (used by `batch.is_current`, the backfill routes and the report scripts) calls a result current when its stored key equals the key of the messages the step would send today, built from the stored upstream results. So a changed prompt, catalog, chapter (intro and people), story line or upstream result outdates exactly the steps that read it, with nothing to bump: there are no version fields. Bump a module's `CODE_VERSION` only when its gate or parsing changes what is stored from the same reply; `decompose.CODE_VERSION` also covers `decompose.parts_from` and `entities.derive_entities`, which are built in code when the decomposition is stored and have no key of their own (bumping it re-asks the model for every decomposition). Seed story records are current as they are. Consistency is kept by clearing on write instead: writing a decomposition clears its icons, flow and resolution; writing a flow clears its resolution; writing another rephrase clears its check. The readers only check that a decomposition was written for the question's text as it is (`decompose.matches`, by `text_hash`).
- **Resume**: with `only_missing` a job skips, per step, what is current. `POST /examination/pipeline/backfill` (`only_missing=true`, `source`, `limit`) starts a `full` job for the questions that lack something, so it resumes a broken import and applies a changed prompt or catalog. Do not edit `.py` files while a job runs under `fastapi dev`: the reload kills it (the backfill then picks up the rest).
- **Report**: `uv run python scripts/pipeline_report.py [DATABASE_URL] [--source FILE] [--show] [--check]` prints, per step, how many questions are current, outdated or missing, the check verdicts, the difficulty spread, the flow views, pre-answer flows that may point at the correct answer (`flow.leak_warning`), and what needs work; `--check` exits 1 when something does.
- **One question**: `uv run python scripts/run_pipeline.py QUESTION_ID [--stages decompose,icons,flow] [--mode full] [--model ...] [--force] [--dry-run] [--show] [--mermaid] [--out FILE]`. A real run starts a one-question job through `batch.run_simplification_job` (same path as the backfill, visible under `/examination/jobs/{id}`) and updates the question's records; `--dry-run` chains the steps' compute functions in memory and writes nothing (objectives and story then use their stored records); `--show` prints the original, the decomposition, parts, entities with icons, the resolution and the rephrase, `--mermaid` the flows. The API's job lock does not cover the script's process (a concurrent write answers 409). `scripts/probe_ica_schema.py` checks whether ICA follows a `json_schema` reply format.

## Prompt evaluation page (`/evaluate`)

A static page, `api/static/evaluate/index.html` (vanilla JS, Mermaid from jsDelivr), served at `/evaluate/ui/` (`app.frontend`), for trying a prompt or gate change on one question: on the left the original, found by id or by its text (anything that is not a 24-hex id goes to `POST /v1/search/questions`; a hit loads by id) with its key, feedback, story and objectives, and the steps to run, on the right the result in pieces (steps, parts, entities, icons, decomposition, beat, flow and resolution with diagrams, the flow built in code, rephrase, check, raw JSON). The flow built in code is an **experiment** (`flow.flow_from`, never stored or served; the game keeps the model's flow): from `scenario_view`, the first event as start, the other events in order, the symptoms as outputs, then the question node with the ask, leaking texts left out; `Result.code_flow` returns it with the flow gate's verdict, `as_json` adds `code_flow`, `code_flow_errors` and `mermaid.code_flow`, and `run_pipeline.py --show/--mermaid` prints it. It is always a **dry run** (`api/pipeline_preview.py`: `Result` and `run_dry`, shared with `scripts/run_pipeline.py --dry-run`): the steps run in memory from the stored records and nothing is written (a dry beat is written on the stored story's stage and feeds the dry rephrase). Routes (`routers/evaluate.py`, behind `require_api_key`; the page itself is open and sends `X-API-Key` from a field): `GET /evaluate/options`, `GET /evaluate/questions/{id}` (`{original, stored}`), `POST /evaluate/questions/{id}/run {stages, model}` → JSON Lines, one line per finished step with the result so far, then `{"stage": "done"}`. Tests: `tests/test_evaluate.py`.

## Decomposition, semantic parts and decision flow (`decompose.py`, `flow.py`)

The spec is `docs/question_decomposition_decision_flow_spec.md`; its two stages are two steps, split by what the player may see before answering.

- **`decompose`** (key-free: the model gets the scenario paragraph, the stem and the answers as neutral candidates, never the key, feedback or explanation): `QuestionDecomposition` (spec §7, trimmed): intent, context with current/desired state, typed entities (`actor`, `system`, `object`, `knowledge_source`, `artifact`, `external_service`, `concept`), events, relationships, problem (symptoms, root causes, consequences), conditions, goals, `answer_options` (what each answer proposes, unjudged), ambiguities. Every entity, event, condition and fact has a `source_status`. Gate `decomposition_errors`: unique ids and resolving references, one answer option per answer, at most 12 entities, no number the question lacks, an `explicit` item quotes `evidence` word for word (normalized) and, unless it is an entity, from the scenario or stem (a quote of an answer would show its mechanism as a fact), no `inferred` root cause (an inferred cause is usually the answer, worked out from what the model knows; an open cause belongs in `ambiguities_and_unknowns`), and no scenario fact, event or condition, whatever its source status, that names an entity only an answer option names or repeats an answer (`leaks.leak_errors`). Stored in `question_decomposition` (`semantic`, `parts`, `entities`, `semantic_ica`, `text_hash`, `input_key`; unique `question_id`) together with everything built on it (icons, flow, resolution), so all of it names the same entity ids; writing it clears the icons, flow and resolution. `DecompositionRecord` reads a stored flow or resolution of an older shape as None.
- **Semantic parts** (no ICA call): `decompose.parts_from` builds the question as `parts` when the decomposition is stored (`SemanticPart`: `role` `context|current_state|problem|consequence|goal|constraint|ask`, `text`, the decomposition `entity_ids` it names): from `scenario_view` (no answer option, no entity only an answer names), the context description, current state, symptoms, consequences, goals and explicit conditions in that order, then the question's own ask word for word (`question_view.the_ask`) as the last part; at most `MAX_PARTS` (6), cut from the end before the ask.
- **Entities** (no ICA call): `entities.derive_entities` builds them when the decomposition is stored: its drawable entities (`entities.VISUAL_KIND`; a `concept` is never drawn) go through `parse_entities` (grounding in the original question and answers, stable actors, no generic names, limits), answers list the entities of their answer option first, and each entity keeps its decomposition id as `VisualEntity.ref` (what a part's `entity_ids` and a flow node's `entity_ids` match). A question without a decomposition has no entities.
- **`flow`** (key-free): `DecisionFlow` (`visualization` primary/secondary/reason, `trigger`, `nodes` `start|process|decision|input|output|human_review|end`, `edges` with `source`/`target`, not `from`/`to`, which is a C# keyword). The model gets the stem and `decompose.scenario_view` (no answer options, no entity only an answer names, no open question or success criterion naming one). The flow ends in exactly one decision node with `is_question: true` and no outgoing edges: the client hangs the answer cards on it; whatever the model draws after it is cut in code (`prune_after_question`, which also drops nodes left without any edge; passed as `ask_validated(transform=...)`, so a repair note shows the pruned reply), and its label is set in code to the question's own ask, word for word (`with_question_label` / `the_ask`: the model's label tended to be a hypothesis such as "Is the failure caused by the max_tokens stop?"). Gate (`flow_errors` / `graph_errors`): one start, edges between existing nodes, every node reachable and able to reach an end, decisions with 2+ labelled branches, a pre-answer decision only on a condition the decomposition marks `explicit`, only decision nodes ask, labels of at most 14 words (the prompt asks for 10; the question node is exempt), at most 14 nodes, resolving ids, no invented number, no trigger, node or edge label that leaks (`leaks.leak_errors`: names an entity only an answer mentions or repeats an answer), nothing `added`. A flow without branching is drawn as `process_flow` / `cause_effect_diagram`. `leak_warning` (soft, in the report; `leaks.points_at_correct`) flags labels sharing clearly more words with the correct answer than with the others.
- **`resolve`** (sees the key, feedback and explanation): it gets the pre-answer flow without its question node and the nodes the learner chose after, and returns `Resolution`: `answer_requirements`, that flow continued with the correct mechanism's steps (marked `added`), per option `verdict`/`supported_requirements`/`gaps`/`reason` (a comparison matrix), and a one-line `rule`. Gate `resolution_errors`: the graph rules (no question node, something added), one option per answer, verdicts matching `correct_response`.
- **Routes**: `GET /examination/{id}/decomposition`, `POST /examination/{id}/decompose|flow|resolve` (409 while a job runs; 404 without the step they need).
- **Game**: `GameQuestion.parts`, `entities` and `flow` (`GameFlow`: flat, empty lists when none) come from the question's decomposition record (`game.domain` `parts_of`, `entities_of`, `flow_of`), when it was written for the question's text as it is; the rephrase item gets the same entities and flow and no parts. The resolution is part of the answer key: it is kept in the round entry (`resolution`) and sent only as `GameAnswerResult.resolution` (`GameResolution`, empty when none), exactly when the flow it continues is sent (`resolution_of`). `QuestionRepository.get_decomposition_many` never reads `semantic`. Search and browse results carry no flow or entities.
- **Found while trying it on real questions**: a key-free model still solves the question from what it knows, so the leak rules above are code gates, not only prompt rules; ICA's `json_schema` is best effort (see `probe_ica_schema.py`).

Tests: `tests/test_decompose.py` (gates, pruning, scenario view, parts, derived entities, structured-output fallback, jobs and routes), `tests/test_game.py` (round and answer result), `tests/test_pipeline.py`, `tests/test_contract.py`.

## The rephrase of a question (`rephrase.py`)

The game is built from the original question, its decomposition, parts, entities and flow. The rephrase is optional: the same question and answers in plain words, from another angle, told as a moment in the story (`examination_simplified.prompt`: `question`, `answers`, index-aligned with the original's; the game may offer it, the original stays what is scored). It is written from `KeyFreeQuestion`: the model never sees the correct answer, feedback or explanation, and it writes no feedback (the review a player gets is the original's). The system message carries the company, the question's chapter and its people; the user message the question split into scenario paragraph and stem, its stage and beat, and an `OPENING` line. Its gate also refuses a rephrased question that gives an answer away (`rephrase.leak_errors`, see `leaks.py`). `rephrase.opening` decides in code who opens the question (one in three gets one of the chapter's people, the rest start with the situation), because the model would open every question with a person.

A reply must pass `_validate_shape` (one non-empty, distinct answer per original answer) and `fidelity_errors` before it is stored:
- every exact term of an original answer is in the rewrite of that same answer, and every exact term of the stem in the rewritten question (`exam_terms.lost_terms`: identifiers found by their form, plus the closed list `exam_terms.TERMS` of named concepts and the spellings that count as the same);
- every number of the stem is in the question as digits;
- no answer is longer than `MAX_ANSWER_GROWTH` times its original.

A failing reply is sent back with what was wrong (`repair_note`), up to `MAX_ATTEMPTS`; after that the call raises 502, which a job retries. A near copy of an answer is only a warning (`quality_warnings`). A question without a chapter gets a text set in the company only. `POST /questions/{id}/rephrase` (`force=true` to redo) writes one; `POST /ica/explain` rephrases an item of the practice-exam file and returns it with the item's own feedback.

## The check: does the rephrase keep the right answer? (`check.py`)

The last step gives the model the rephrase and its answers, key-free. If it picks the correct answer the verdict is `same`. If not, it is asked the original the same way: right there means the rewrite is at fault (`changed`), wrong there too means the question is hard in any wording (`hard`). The result is stored on the rephrase record (`check`: `verdict`, `picked`, `picked_original`, `input_key`, `ica`); `rephrase_and_store` clears it when the text changes. `game.domain.simplified_matches` refuses a `changed` rephrase, so the game offers only the original for that question. `POST /examination/{id}/check` checks one question; job mode `check` exists for backfills.

## Icons of a question (`icons.py`)

After the decomposition, an ICA call picks from the closed list in `api/icon_catalog.py` one key per entity, one for the question and one per answer (what that answer proposes, so cards of one question differ). It reads `KeyFreeQuestion` (the stem and answers) and the entities' names, kinds and aliases. `ICONS` is `(key, meaning, lucide)`: the stored data and `/v1/game` carry only the provider-neutral `key`; `meaning` is what the model reads; `lucide` is today's picture and is used only by `scripts/export_game_icons.py`, which writes `<key>.svg` into the game (`--check` compares, `--force` rewrites). Changing the icon set is a change to that script and the game's files, not to the data. Stored on the decomposition record as `entities.question_icon`, `entities.question[].icon`, `entities.answers[].icon`, `entities.answers[].entities[].icon`, plus `icons_ica` and `icons_input_key` (conditional on `updated_at`, else 409; a new decomposition clears them). `parse_icons` rejects a wrong shape with 502 but repairs single picks: an entity without a known key gets its kind's key (`KIND_FALLBACK`), an answer the icon of its least shared entity, the question that of its first entity. `POST /examination/{id}/icons` (404 without a decomposition, 409 while a job runs) and `POST /examination/icons/backfill` (job `mode="icons"`, decomposed questions whose icons are not current) run it alone; `icons_failed` counts questions whose earlier steps were stored but whose icon step failed. `game/domain.py` `entities_of` serves a key that left the catalog as null (the game then draws a fallback). After adding a key: run the export script and `UPDATE_CONTRACT=1 uv run --with pytest pytest tests/test_contract.py` (`tests/contract/icon_catalog.json` is copied to the game, whose tests check it ships every key). Tests: `tests/test_icons.py`, `tests/test_entities.py`, `tests/test_jobs.py`.

## Learning objectives of questions

A separate ICA step (`api/objectives.py`) tags each question with learning objectives. It reads the ORIGINAL question with its answer key, feedback and explanation, and writes its own collection, `question_objectives` (one record per `question_id`, unique index; model `QuestionObjectives`): `objectives` (keys, the main one first, at most two more), `level` (`remember`/`understand`/`apply`/`analyze`), `tempting` (indices of the wrong answers that would partly work), `difficulty` (1-3, derived by `objectives.difficulty_of` from `level` and the number of tempting answers; the model's own estimate came out as 2 for nearly every question), `distractors` (one per answer: `null` for a correct answer, else `{misconception, confused_with}`: what a learner who picks it wrongly believes, and the objective that answer would be right for), `input_key`, `ica`.

- **Catalog:** `api/objective_catalog.py` is a closed, hand-approved list `ObjectiveDef(key, section, title, statement)`; `section` is the question section without its `Domain N: ` prefix (`normalize_section`). The model reads `statement`; a client shows `title`. This file is where objectives are enforced: edit it by hand. `scripts/propose_objectives.py "<section>"` asks ICA for a proposal from the section's questions and prints `ObjectiveDef` lines to review; it changes nothing.
- **Gates:** `parse_objectives` rejects (502, retried by a job) an unknown main objective, a bad level, a `tempting` that is no list, a wrong number of distractors, a misconception on a correct answer and a wrong answer without one. The model returns its distractors keyed by answer letter (wrong answers only), because a position in a list proved easy to get wrong; the stored list is still index-aligned. Nothing is repaired with a guess; only an unknown secondary key or `confused_with` is dropped. The main objective may belong to another section than the question's (the source's sections overlap). A question whose section has no objectives, or without an answer key, is 422 and not retried.
- **Outdated:** the section's objectives (keys, sections, statements) are in the tagging prompt, so editing the catalog or the prompt changes the input key of the questions that read it, and the next backfill tags those again (a title change doesn't count).
- **Running it:** `POST /examination/objectives/backfill` (`only_missing=true`, optional `section`, `limit`; job `mode="objectives"`, tracked like the other jobs) and `POST /examination/{id}/objectives` for one question. It is also the first step of the import's `full` job; a question whose section has no objectives fails that step only (the import's dry run lists such sections as `unknown_sections`).
- **Report:** `uv run python scripts/objective_coverage.py [DATABASE_URL] [--min N] [--check]` prints questions per objective by difficulty, sections without objectives, thin objectives, untagged and outdated questions and the most frequent `confused_with` pairs; `--check` exits 1 when something needs work.
- **Game:** `GameQuestion.objectives` (keys still in the catalog; `[]` when untagged) and `difficulty` (0 when untagged) on round, batch and added questions (search and browse results are untagged); `GameRoundRequest.objective` keeps only questions tagged with that key (stored in the round's `filters`, so batches keep it); `GET /v1/game/objectives` lists the catalog with playable counts. The misconceptions are part of the answer key: they are stored in the round entry (`misconceptions`) and only `GameAnswerResult.misconception`, for the answer given, is ever sent. `confused_with` is not sent yet.

Tests: `tests/test_objectives.py`, `tests/test_jobs.py` (job mode, versions, routes), `tests/test_game.py`.

## The game's story (main scenario)

The game frames the bank as one story: the player is the Claude architect of one company, each exam scenario is a chapter, and every chapter has the same five stages. A chapter's stage is one stop on the game's (planned) map.

- **Catalog:** `api/scenario_catalog.py` is closed and hand-approved, like the objective catalog: the company (`COMPANY`, `COMPANY_INTRO`), `SCENARIOS` (`ScenarioDef(key, title, district, intro, outro, marker)`, in play order) and `STAGES` (`design`, `build`, `team`, `incident`, `scale`). Source questions are `SCENARIO: <paragraph> QUESTION: <stem>` and the paragraph repeats word for word, so `scenario_of(doc)` reads the chapter from the text (the chapter whose lower-case `marker` the paragraph contains) with no model call; `stem_of(doc)` is the question without the paragraph. A paragraph no chapter claims (`unknown_paragraph`) leaves its questions without a chapter until one is added here; `scripts/propose_scenarios.py` lists such paragraphs with a `ScenarioDef` skeleton. A question with no paragraph at all gets its chapter from the model in the story step. Each chapter has a `cast` (two named people with a role), the only names a model may use, so all questions of a chapter are brought by the same few people.
- **Records:** `question_story` (one per `question_id`, unique index; model `QuestionStory`): `scenario`, `stage`, `order` (position inside the stage), `beat` (one line shown before the question, written key-free by `api/beat.py` or by hand in the seed; "" until then), `beat_ica`, `beat_input_key`, `win` / `fail` (one line shown after a correct / wrong answer), `text_hash` (`scenario_catalog.text_hash` of the question's text and answers), `origin`, `scenario_origin` (`text`, or `model` when the model picked the chapter of a question without a paragraph), `input_key` (model-written records), `ica`. The question and its answers are never rewritten. A record whose `text_hash` no longer matches the question is ignored when serving (`game.domain.usable_story`).
- **Two writers:** `origin: "seed"` records are hand-written in `data/story_seed.json` (items name a question by `hash`; their order inside a chapter's stage is the play order) and loaded with `uv run python scripts/load_story_seed.py [DATABASE_URL] [--dry-run]`, which refuses to write anything when an item is invalid or matches no question. `origin: "ica"` records come from `api/story.py` (`write_story`, `story_and_store`), which gives the model the company, the chapter's intro and people (or all chapters, when it has to pick one), the stage list, three seed lines as examples of the style and the stem with its key; they get `order` 1000 plus the question's difficulty, so they come after the seeded ones, easier first. Both go through `parse_story` (502, retried by a job: unknown stage or chapter, an empty line or one over 20 words (30 for the seed), a `win` / `fail` that repeats the correct one, and for the seed (`with_beat=True`) a beat that repeats an answer). The model writes no beat; `story_and_store` clears `beat`, `beat_ica` and `beat_input_key` (the beat was written for the old stage). A question with an unknown scenario paragraph or without an answer key is 422.
- **The beat** (`api/beat.py`, key-free): `messages(q, place)` from `KeyFreeQuestion` plus the company, the chapter with its people and the stage of the story record (never an earlier beat), the stem and the answers the player will see ("name or hint none"); gate `beat_errors` (one line of at most 20 words, `leaks.leak_errors` with the decomposition when there is one) through `ask_validated`. `beat_and_store` writes `beat`, `beat_ica`, `beat_input_key` on the story record, conditional on its `updated_at` (409 otherwise); 404 without a usable story record. A seed record's beat is current as it is (`pipeline_keys`); one without a beat gets one written. `POST /examination/{id}/beat` rewrites one (a seed's too).
- **Running it:** `POST /examination/story/backfill` (`only_missing=true`, `limit`; job `mode="story"`: story and beat) skips questions whose story and beat are both current (seed records count as current) (by input key: a changed chapter intro, cast or prompt outdates only the questions that read it), so it mostly costs ICA calls for new imports; `POST /examination/{id}/story` rewrites one question, a seed record included (load the seed again to restore it), and clears its beat: write that again with `POST /examination/{id}/beat` (a story job does both). It is also the second step of the import's `full` job.
- **Report:** `uv run python scripts/story_coverage.py [DATABASE_URL] [--min N] [--check]` prints questions per chapter and stage, scenarios no chapter claims, questions without a usable record, outdated ICA records and the main objectives per chapter.
- **Game:** `GameQuestion.scenario` and `stem` come from the text (so they need no record; `stem` is "" without a chapter and on rephrases, which never repeat the scenario paragraph), `stage` and `beat` from the record. For a question without a scenario paragraph the chapter comes from its story record (`game.domain.chapter_of`) and it has no stem. `win` / `fail` are kept in the round entry (`outcomes`) and only `GameAnswerResult.outcome`, for the answer given, is sent. `GameRoundRequest.scenario` / `stage` keep only questions whose record has them, and with `ordered` the round and its batches serve them in story order (chapter, stage, `order`) instead of sampling (`GameService._pick`). `GET /v1/game/story` returns the company, chapters and stages with playable counts.

Tests: `tests/test_story.py` (catalog, parser, seed file and loader), `tests/test_jobs.py`, `tests/test_game.py`, `tests/test_contract.py` (`story.json`).

## Question search API (`/v1/search`)

`GET /v1/search/questions?q=&section=&assessment_type=&limit=5` (`src/claude_exam/api/routers/search.py` → service `src/claude_exam/api/search.py` → MongoDB `examination`) replaces the Obsidian card search for the lookup skills. It runs a `$text` query against a weighted text index (`examination_text`, created in the app `lifespan`: `prompt.question` 10, `section` 3, `prompt.explanation` 2, `prompt.answers` 1) and ranks by `{$meta: "textScore"}`. `q` is 2–2000 chars (`SEARCH_TEXT_MAX`; the game lets players paste a whole question), `limit` 1–50, empty `section`/`assessment_type` mean "any". `search.plain_terms` strips the `$text` operators from `q` before searching (double quotes would make every phrase required, a leading `-` would exclude a word, so a pasted `--max-turns` hid the question that mentions it). Each search route also takes `POST` with the same fields as a JSON body (`SearchRequest`), for texts too long for a URL: percent-encoded, a pasted question can pass a server's or proxy's request-line limit, which answers 400/414 without the API's error body.

Response is `{items: SearchHit[], total}`; `SearchHit` = `id, score, section, assessment_type, question, answers[], correct_answers[], explanation`. **It does return the answer key** (it backs the study skills), so keep it separate from `/game`, whose responses never reveal answers before answering. Like `/questions`, it is open unless `API_KEY` is set (then it needs `X-API-Key`).

Differences from the old card search: Mongo questions have no title or tags (so no title/tag bonuses), `$text` stems and drops stopwords but does not match partial words, and scores are not comparable to the old overlap scores. `short-question-answer`, `extended-question-answer` and `vault-tutor` now call this endpoint; `vault_scan.py`, `search_cards.py` and the `claude-exam-vault` MCP server remain in place but are unused by them until removed.

`GET`/`POST /v1/search/game-questions` (same parameters; the game sends the `POST`) is the game's search: only playable questions (`PLAYABLE_QUERY` + `is_playable`), returned as `{items: GameQuestion[], total}` **without** the answer key or score. To play a hit, the game adds it to its round with `POST /v1/game/rounds/{round_id}/questions`. The `/search` routes are rate limited (120/min per client), and `/search/questions` needs the API key when `API_KEY` is set.

Tests: `tests/test_search.py` (fake collection with chainable `find().sort().limit()`).

## Card-authoring skills

These three skills retrofit or create cards under `Questions/` — distinct from the four read-oriented skills below, which only ever look cards up:

- **`roadmap-linker`** — adds the `Roadmap: [[Step Title]]` reference line and, where warranted, a roadmap-derived tag, linking a card to its place on the `roadmap/` study path.
- **`keyword-highlighter`** — adds sparing `==highlight==` markup correlating a card's Question to its Answer/Explanation (see "Question card format" above).
- **`promote-staged-cards`** — turns a `.staging/*.pending.json` record into a real card (title, folder, tags authored by hand from the record's already-cleaned question/answer/explanation), then explicitly invokes `roadmap-linker` and `keyword-highlighter` on it as its last step. This is the intended entry point whenever new practice-exam questions get added to the vault — the other two skills otherwise only run when a card is edited later or the user asks for them by name.

## The four vault skills

Each skill under `.claude/skills/` has a distinct, deliberate output contract — preserve these when editing:

- **`short-question-answer`** — Bash + the `search_cards` CLI. Returns **only** the matched card's `### Answer` text verbatim plus its tags as hashtags — never Question/Explanation/References/frontmatter, never added commentary. For plain "what's the answer to X" lookups.
- **`extended-question-answer`** — the `claude-exam-vault` MCP tools (`search_vault` + `get_card`). Returns the **full card verbatim** (Question, Answer, Explanation, References, tags) — still no paraphrasing or commentary, just more of the card. For lookups where the user also wants the explanation/references.
- **`vault-tutor`** — the same MCP tools, but reasons in Claude's own words: rephrases a confusing question/answer in simpler language, or expands on a card's explanation when the user says it didn't help. The only one of the first three that produces freeform prose rather than verbatim card text.
- **`rate-card`** — the only skill that writes. Takes a rating (0-100) and/or note the user just stated about a card already discussed in the conversation, and persists it via the MCP `update_card` tool. Never fabricates a value, never replaces prior notes (always appends), never touches Question/Answer/Explanation/References/tags.
